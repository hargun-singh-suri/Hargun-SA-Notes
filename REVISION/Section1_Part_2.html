Software Architecture & Design of Large-Scale Systems — Michael Pogrebinsky

Functional vs Non-Functional Requirements

  • Functional = what the system must do. Example: "a user can post a comment"
  • Non-functional = how well it must do it. Example: "a comment must appear within 200ms"
  • Non-functional requirements are really just another name for the quality attributes you already met in Part 1
  • Always separate the two early — mixing them makes requirements gathering confusing

Coupling & Cohesion

  • Coupling = how much one component depends on another's internal details. Aim for low coupling
  • Cohesion = how focused a single component's job is. Aim for high cohesion
  • This is the actual reason "loosely coupled architecture" (Part 1, System Constraints) helps you survive changing constraints
  • Rule of thumb: each component should do one job well, and know as little as possible about other components

Capacity Estimation (Back-of-the-Envelope Math)

  • Before designing anything, estimate the scale you're building for — rough numbers are enough
  • These numbers decide real architecture choices: do you need caching? sharding? horizontal scaling?
  • Redo this estimate whenever a major requirement changes — scale drives design more than any single feature
