REST API — the Basics

  • REST treats everything in your system as a "resource" (a user, an order, a comment) with its own address (URL)
  • You act on that resource using standard HTTP verbs — no custom function names needed
GET/users/123/orders
HTTP VerbMeaningExample
GETRead a resourceFetch a user's profile
POSTCreate a new resourcePlace a new order
PUTReplace a resource entirely (idempotent)Overwrite a user's full profile
PATCHUpdate part of a resourceChange just the user's email
DELETERemove a resourceCancel an order
  • Stateless: every request carries everything needed to handle it — the server doesn't remember you between requests

RPC vs REST — Which Feels Like What

RPC — action-based
  • Feels like calling a function: createOrder(), cancelOrder()
  • Natural fit for internal, service-to-service calls
  • Tighter coupling between client and server code
REST — resource-based
  • Feels like addressing a thing: POST /orders, DELETE /orders/9
  • Natural fit for public APIs used by many different clients
  • Looser coupling — same verbs work on any resource

Two Ideas From Part 1, Made Concrete

Idempotency, worked example

  • POST /payments called twice by accident = charged twice ❌ (not idempotent)
  • PUT /payments/txn-88 called twice = same single payment ✅ (idempotent, safe to retry)

API Versioning, two common ways

  • URI versioning: /v1/orders → /v2/orders — simple, visible in the URL
  • Header versioning: same URL, version sent in a request header — cleaner URLs, less obvious to clients
